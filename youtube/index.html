The small features are part of the job.

Making a video is only part of running a channel. The upload, the related-video link, and the conversation underneath it matter too.

The related-video worker now has a signed Firefox extension on the Dell. It survived a Firefox restart, and browser autostart is configured. I also found a lesson hiding in the queue: a video moving into “published” state must not disappear from unfinished work.

Pinned comments are the next piece. The draft question already exists in the script; the new worker is designed to post it, pin it, reload, and verify it. It stays disabled until signing, installation, and a live test are complete. An uncertain attempt should stop for review rather than post the same comment twice.

0317–18 October 2026Build log

An old Dell gets a new job.

The goal became simple: let the main PC turn off without taking the whole project with it.

The Dell is an old two-core machine with 4GB of RAM. That changes the design: lightweight services, limited parallel work, and software that actually supports its processor. A newer dependency was not automatically a better dependency for this hardware.

A dedicated runner and separate production environment now let it take on second-channel rendering jobs without replacing the existing worker setup. A short three-voice message-story render passed on the Dell. That proves the pieces can run there; it does not yet prove full-length daily throughput.

The second format, Wizzy Posts, uses original fictional chats over supplied Minecraft parkour. It has its own voices, bubble timing, and upload credentials. Its public launch remains gated while verification and private upload checks are unfinished.

Lesson 03Reusing hardware works best when the workload respects its limits.

0214–16 October 2026Build log

Turning a finished clip into a repeatable process.

A good one-off render is encouraging. A workflow has to handle the days when something goes wrong.

The project moved toward separate stages for research, script review, narration, editing, and uploading. Wizzy Rant grew beyond Roblox-specific topics into youth-focused commentary on entertainment, sport, technology, and unusual human stories. Gameplay became the visual format rather than the limit on what the channel could cover.

Free local narration, captions measured against the actual speech, and supplied sound effects became reusable ingredients. The delivery took a few rounds of tuning: speed and pitch needed to apply to the whole take so it still sounded continuous.

The less visible work was just as important: retain drafts, verify the channel before uploading, keep credentials private, and record progress so a failed run cannot blindly upload again. Source checks and editorial review belong before publication.

0111 October 2026The beginning

“Can you automatically make Roblox rants?”

That was the starting question. Before a runner, a queue, or a second channel, there was just a format I wanted to try.

The early experiments combined gameplay, a short original script, synthetic narration, centered captions, topic images, and sound effects. Getting those parts on a timeline was the first challenge. Making the result feel paced for a phone screen was the next.

Every attempt made the preferences more concrete: a stronger hook, less filler, readable captions, relevant visuals, and an audible whoosh when an image appears. The aim was to learn the format by actually making things, then turn the repeated work into tools.

This journal keeps that trail visible. It is a record of a build in progress—not a claim that automation guarantees views, growth, or income.

Lesson 01Start with one finished video. Learn what needs repeating.

↗Practical notesWorkflow guide

How the pieces fit together.

This is the structure behind the project. Each step has a result to check before the next one begins.

  1. Choose a format and write the brief.

    Define the audience, pacing, narration, visual style, and what counts as a finished video. Start with a manual example you actually like.

  2. Prepare the story.

    For commentary, check reporting and distinguish facts from opinion. For the message channel, write original fiction and keep it clearly fictional. Review the hook, escalation, and ending.

  3. Build and inspect the video.

    Generate narration, measure caption timing, choose a usable gameplay segment, and render the visuals and sound. Watch the result before trusting the recipe.

  4. Test uploading privately.

    Authorize the correct channel, keep each channel’s credentials separate, and verify the uploaded video. Save progress so a retry cannot accidentally create another upload.

  5. Finish the channel details.

    Check title, description, scheduling, related video, and discussion comment. Treat browser-only steps as separate features that need their own live verification.

  6. Learn from the output.

    Review actual performance when data is available. Change one useful thing at a time, document the result, and keep unfinished experiments separate from the working setup.
